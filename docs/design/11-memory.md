# 11 — Memory as a harness feature

Status: decided 2026-10-10 (Jason, with the personal-kb lead session). Phases 1 and 3 shipped in v0.15.0, default-off in the binary; the dispatch fleet runs `--memory annotate` since 2026-10-11, with the pre-registered kb-bench test (H-013) running alongside and deciding between annotate, deny-once and off. Phase 2 waits on its kb-bench eval.

## Decision

Talos consumes the personal-kb experience loop natively, inside the engine loop, not through MCP or hooks. Claude Code can only reach the KB through hooks (session start, PreToolUse deny, Stop transcript digest) and an MCP server; talos owns the tool dispatch, the context window, compaction and its own verdicts on the agent's work, so memory can be a first-class harness feature with more control than a hook can have.

## Why the harness and not hooks + MCP

- **Delivery at the moment of use, at no turn cost.** The Claude Code soft gate can only deny a Bash command matched on a two-word target class, and kb-bench measured that a deny on top of the session slice "adds nothing and costs a turn" (KB kb-03673). Talos sees every tool call before it runs and can attach the relevant fact to that tool's result instead, or deny once when the evidence says denying is better.
- **Memory that survives compaction.** Talos owns the compaction tiers (design 08), so delivered facts can be protected the way the system prompt and task spec already are.
- **Capture without a human.** Headless runs never produce the user corrections the KB's shape-2 capture relies on, but talos corrects its own agent all the time: a gate that goes red then green, a `finish(done)` rejected by claim verification, a no-change rejection, a nudge. Those are recorded with full reasoning, and they are the headless analogue of a user correction with ground truth attached.
- **It is measurable.** The Harbor `TalosAgent` is validated (design 09), so a talos arm in kb-bench runs on the same images and scenarios as the Claude Code arm.

## Decisions of record

- **Seam:** a generic `Memory` seam on `RunConfig`, a no-op by default, with one adapter (personal-kb over HTTP). Nothing speculative beyond that one adapter.
- **Delivery mode:** annotate the tool result first; deny-once exists as a separate mode so kb-bench can run it as its own arm. Release only after kb-bench shows the feature helps, ideally in deny-once mode.
- **Default off** (`talos run --memory off|annotate|deny-once`), per this repo's rule that harness features ship default-off and flip only after tier-2 shows benefit and the tier-1 perfect-spec guard stays clean.
- **Eval isolation:** tier-2 and kb-bench runs use the seeded offline KB or memory off, never the live KB, so it cannot leak facts about benchmark tasks into runs.
- **Relevance lives in the KB service,** shared by both harnesses. Talos keeps a local first stage (the cached index plus a cheap prefilter) so most tool calls touch no network, and asks the KB only about the rest, failing open at 1 s.
- **Agent access (revised 2026-10-10):** talos is an MCP client of the KB, and does not hand-port the agent-facing tools. kb-service serves its MCP tool set over HTTP with the REST API's bearer auth, and the local stdio MCP server is retired. Claude Code and talos then consume one tool definition, in Python, and an API change ships once on the server instead of being reinstalled on every machine. Only the automation endpoints (`/prevention`, later `/turn`) are native Rust, because their behaviour is harness logic. They are guarded by golden request/response fixtures that kb-service publishes and that the Claude Code hook and talos both test against.
- **Agent writes (revised 2026-10-10):** the write policy lives in the KB server and covers every surface. A `kb_store` from a headless or autonomous caller, whether Claude Code's MCP in a dispatch run, talos, or anything unattended, goes through the candidate pipeline (distiller, critic, 30-day expiry unless re-observed), while interactive, deliberate stores behave as today. That gives one write path with provenance-driven routing, so it stays possible to tell what happened and why. It replaces the earlier talos-only `kb_note` tool and `agent_note` digest item.
- **Clef:** measured 2026-10-10 by the KB lead on 1,677 real bench commands (KB: 'Gate matcher eval'). Lexical P=0.78 R=0.36; clef-flash at threshold 0.7 P=0.51 R=0.67, p95 2.6 s on the GPU host under load. That fails the pre-registered bar, so **deny stays lexical** (the phase-1 `cues_lite` port is the deny matcher). Clef does recover lessons that have no command cue at all (stop-hook R=0.87 at P=0.95, wireguard R=0.85, where lexical scores 0), so a non-blocking, Clef-driven annotate channel is a candidate, but only after its own kb-bench eval (a talos or Claude Code annotate arm). The KB's per-call advice endpoint stays unbuilt until then (personal-kb GTD 852ded69).

## Phases

1. **Read path (building now).** The `Memory` seam and engine wiring (session slice into the system prompt, `before_tool` advice applied as annotate or deny-once, transcript telemetry for every decision), the personal-kb adapter (`GET /api/kb/prevention` at run start, cached index, a port of the hook's lexical matcher), the `--memory` flag and a `TalosAgent` kwarg. Agent-facing KB tools come from a generic talos MCP client (built against a fake server, integration-tested once kb-service serves MCP over HTTP). Measured as a talos arm in kb-bench.
2. **Clef-driven annotate (conditional).** Only if a kb-bench annotate arm shows that Clef's extra recall on cue-less lessons helps more than its lower precision hurts: talos sends non-matching calls to the KB's advice endpoint for annotation (never deny), failing open at 1 s. Deny stays on the lexical matcher regardless.
3. **Native capture.** Turn digests to `POST /api/kb/turn` with `harness: "talos"`, carrying `reasoning`, and `harness_correction` (trigger `gate_red | claim_rejected | no_change | nudge`, detail, `resolved_by` tool-use ids, `resolved`) items. Shadow vs live capture is decided server-side by the KB's service setting and the API key's surface, and talos sends nothing for it. Failed tool calls also go separately: with `--memory annotate|deny-once`, talos posts each failed `bash`, `edit_file`, `read_file` or `list_files` call to `POST /api/kb/event` (record-only on the KB side), capped at 50 per run.

   Digests are periodic within one KB session: `session_id` is the run's kb session id, `turn_index` runs 0, 1, 2, ... and `event_id` is `<session_id>:<turn_index>`. A digest closes when the next item group would push it past 200 items or 65,536 bytes, or at an iteration boundary once 10 minutes have passed since it opened; mid-run digests are spawned, never awaited, and a final digest is always sent at run end inside the existing 3 s bounded flush. The rationale is that a SIGKILLed or OOMed run never sends an end-of-run digest, and long fleet runs are the ones most worth learning from.

   The engine reports the four triggers through one `Memory::observe` hook: `gate_red` (a red `run_checks`), `claim_rejected` (a `done` or `already_satisfied` rejected by red checks), `no_change` (a `done` on an unchanged tree) and `nudge` (a finish-recovery nudge). The adapter owns the lifecycle: a repeat of an open trigger folds into it, and every open correction resolves uniformly at the next green `run_checks` or accepted `done`/`already_satisfied`/`answer`, with `resolved_by` naming the posted calls in between; one still open at run end goes into the final digest with `resolved: false`.

   Every digest and event POST carries `X-KB-Engine: <model id>` (the provider-verbatim model id, e.g. the `OLLAMA_MODEL` value).

## KB-side contracts (agreed with the KB lead, owned on the personal-kb board)

Talos sends its native tool names with `harness: "talos"` and the KB maps them to its canonical names: `bash`→Bash, `edit_file`→Edit, `read_file`→Read, `list_files`→LS. Talos has no `write_file` (edit_file also creates files), and `list_files` lists a directory tree, so it maps to LS rather than Glob; `run_checks` and `finish` have no Claude Code equivalent. The KB owns this map (kb-service `harness_tools.py`) and returns it as `tool_map` on `/prevention` when the caller identifies as talos, by the `harness=talos` query parameter or the `X-KB-Harness` header. The index stays in canonical names, so talos translates its native name through `tool_map` before matching, and treats a response with no `tool_map` key as an older KB. For a mapped harness the KB returns the index regardless of Claude Code's gate switch, and talos applies its own `--memory` mode. Talos sends `harness=talos`, translates its native names through `tool_map`, ignores the gate switch, and keeps no cues from a KB that omits `tool_map`. The digest gains optional `reasoning` and `harness_correction` item kinds, and the KB treats `harness_correction` as a deterministic capture shape. The KB side also owns MCP over HTTP, the server-side write policy, and the golden fixtures for `/prevention` and `/turn`.

Talos posts only calls whose native name is a `tool_map` key as `tool_call`/`tool_result` digest items (KB MCP tools and `--mcp` tools never appear), with `tool_use_id` = `<iteration>:<call id>` so ids are unique per session even when a backend reuses call ids every turn (Ollama's `ollama-call-<i>`).
